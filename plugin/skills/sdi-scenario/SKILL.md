# /scenario — natural-language → GWT

This skill is the **LLM-side normalisation surface** for SDI's first-class
behavior unit. The user speaks freely; you (the LLM) restate the intent as a
**G/W/T triple** with all three clauses non-empty, and persist it through
`sdi scenario create`. The daemon rejects empty clauses with `GWT_EMPTY` —
the discipline is yours, not the user's.

> **Lineage**: BDD `.feature` files used Gherkin syntax that humans had to
> learn and step-glue had to bridge to code. SDI keeps the G/W/T structure
> (atomicity benefit) but drops Gherkin syntax + step glue (the LLM reads
> natural language directly).

---

## When to invoke

Trigger this skill when the user describes a **behavior the system must
exhibit** — even informally. Examples:

| User says | Your move |
|---|---|
| "로그인 폼 빈칸 검사 좀 넣어줘" | One scenario: G=폼이 비어 있다 / W=submit 클릭 / T=오류 메시지 표시 |
| "결제 실패하면 재시도 화면" | One scenario per failure mode (network / declined / timeout) — atomic split |
| "검색이 빠르면 좋겠어" | NOT a scenario yet — clarify into "p95 ≤ 200ms on N=10k corpus" before authoring |

Don't invoke this for:
- **Constraints / facts / input data** → use `/req` (Requirement, snapshot).
- **Rationale for choosing X over Y** → use `/decide` (Decision, append-only).
- **Plan / round / task lifecycle** → use the matching slash command directly.

---

## The atomicity rule

One scenario = one testable assertion. If you find yourself writing "and also",
"unless", or commas separating multiple Whens / Thens, **split** into separate
scenarios.

✗ Bad — multi-assertion drag:
```
Given: 사용자가 로그인됨
When:  /profile 에서 'save' 를 누른다
Then:  API 가 200 + DB 반영 + 토스트 표시 + 이력 기록
```

✓ Good — four scenarios:
```
SC-PROFILE-01  G:로그인 W:save 클릭 T:API 200 반환
SC-PROFILE-02  G:save 200 직후 W:DB 조회 T:변경 필드가 새 값으로 보임
SC-PROFILE-03  G:save 200 직후 W:UI 관찰 T:'저장됨' 토스트 표시
SC-PROFILE-04  G:save 200 직후 W:audit 로그 조회 T:이력 1건 추가
```

Many small scenarios > one big one. Round R(N+1) verifies them independently,
so atomicity is what gives you fine-grained regression signal.

## The clause discipline

| Clause | Captures | Anti-pattern |
|---|---|---|
| **Given** | Pre-condition: state + actor + context required for the behavior. | "사용자가 있다" (under-specified — what state?) |
| **When** | The single trigger: an action, event, or arrival of input. | "사용자가 사이트를 쓴다" (not a trigger — when exactly?) |
| **Then** | The observable result: API return, persisted state, rendered output. | "잘 동작한다" (not observable — what specifically?) |

Each clause must be **observable** by either the LLM (file:line, HTTP
transcript, DB row) or the user (rendered UI). "It feels good" is not a Then.

## The persist call

Once the triple is normalised:

```bash
sdi scenario create <PLAN-ID> <SHORT-CODE> \
  --given "<given clause, single sentence>" \
  --when  "<when clause, single sentence>" \
  --then  "<then clause, single sentence>" \
  --confirmed
```

- `<PLAN-ID>`: use `sdi plan active <PROJECT-ID>` if the user didn't pin a
  plan. The active plan is the one currently in `active` status.
- `<SHORT-CODE>`: human ticket suffix per plan, e.g. `SC-12` or
  `SC-PROFILE-01`. The daemon enforces per-plan uniqueness.
- `--confirmed`: flip immediately to `confirmed` when the GWT triple is final.
  If you're still drafting alternatives for the user to pick, omit it (drops
  in `draft`).

After success, repeat for each scenario in the user's description. Don't try
to fit multiple behaviors into one call.

---

## GWT non-empty failure recovery

| Code | What happened | Self-fix |
|---|---|---|
| `GWT_EMPTY` | One of `--given` / `--when` / `--then` was empty or whitespace. | Fill the missing clause; resubmit. Never paper over with `"n/a"` — write the real clause. |
| `CONFLICT` | `short_code` already taken on this plan. | Increment the suffix (`SC-12` → `SC-13`). The user's naming preference wins if they specified one — bump within the prefix family. |
| `NOT_FOUND` | Plan id wrong. | Re-resolve via `sdi plan active <PROJECT-ID>`. Register the cwd first if there's no project: `sdi project create <KEY> "<name>" --cwd "$(pwd)"`. |

## Plan approve gate reminder

After authoring scenarios, the user can run `sdi plan approve <PLAN-ID>`. The
daemon returns `SCENARIOS_REQUIRED` if **zero confirmed** scenarios exist.
Task count does not matter — tasks are runtime artifacts generated by the LLM
after approval, not first-class entities the user authors upfront. The
approval gate is "verifiable behaviors exist," not "work breakdown exists."

So: when the user asks to approve, first check that at least one of your
authored scenarios is `confirmed` (not just `draft`).

---

## What you do NOT do here

- **You don't run rounds.** That's `/round activate` after `/plan approve` —
  see `sdi-round`.
- **You don't decompose tasks.** Tasks emerge as runtime artifacts at round
  activation; scenarios are the durable spec, tasks are the runtime work
  units. See `sdi-round`.
- **You don't edit a scenario's body to record "changed our minds".** Plan /
  scenario / requirement bodies are snapshot-only — updates overwrite in
  place, no version history in the body. If the behavior spec changes,
  overwrite in place; if you want to record the reason, use `/decide`.
  Append-only history lives in decisions, never in scenario bodies.
